### 3.5 主画布

#### 3.5.1 泳道背景层

泳道背景用 DOM div 实现，位于 ReactFlow 画布下层（z-index 更低）。

**泳道配色方案：**

不同泳道拥有不同的背景色，用于视觉上区分泳道区域。配色选用低饱和度柔和色，不喧宾夺主。

| 颜色 | 格子背景 | 标题底色 | 标题文字色 |
|------|----------|----------|------------|
| 蓝 | `bg-blue-50/60` | `bg-blue-100` | `text-blue-800` |
| 翠 | `bg-emerald-50/60` | `bg-emerald-100` | `text-emerald-800` |
| 琥 | `bg-amber-50/60` | `bg-amber-100` | `text-amber-800` |
| 紫 | `bg-violet-50/60` | `bg-violet-100` | `text-violet-800` |
| 玫 | `bg-rose-50/60` | `bg-rose-100` | `text-rose-800` |
| 青 | `bg-cyan-50/60` | `bg-cyan-100` | `text-cyan-800` |

- 按泳道索引循环取色（6色循环）
- 同一 Participant 行内所有格子共享该行的背景色
- 自定义泳道列标题的底色按列索引取色
- 所有泳道标题文字加粗加黑（`font-extrabold` + 对应深色文字色）

**默认泳道：**

- 所有流程图至少有一个默认自定义泳道，默认名称为「活动流程」
- 新建流程时自动创建该泳道，用户可重命名或删除（但删除后如无其他自定义泳道需重新创建）

**Participant 横向排列时：**

```
┌─────────────────────────────────────────────────────────────┐
│ 客户  │                                                    │
│       │  ┌─────────┐        ┌─────────┐                   │
│       │  │ 提交订单 │ ────▶  │ 支付判断 │                   │
│───────┼──┴─────────┴────────┴─────────┴───────────────────│
│ 系统  │                         │        │                 │
│       │                    ┌────┘        └────┐          │
│       │                    ▼                  ▼          │
└─────────────────────────────────────────────────────────────┘
       ↑
       自定义泳道纵向排列（左右）：初始阶段 | 交易阶段 | 完成阶段
```

**节点位置约束：**

- 每个节点必须落在其所属泳道交叉区域内，或在拖拽过程中自动拓展泳道以适应
- 节点拖拽时：
  - 若节点边缘超出当前泳道边界，但节点中心点仍在当前泳道内 → **自动拓展泳道尺寸**以容纳节点（留 8px 边距）
  - 若节点中心点超出当前 Participant 泳道，进入另一 Participant 泳道 → 弹出确认 Dialog（见 §4）
  - 若仅跨越了 Custom 泳道边界 → 自动更新 `customLaneIndex`，无弹窗
- 拓展规则：
  - 自定义泳道（纵向列）：节点右侧超出时自动增加列宽
  - 角色泳道（横向行）：节点底部超出时自动增加行高

**泳道分隔线 resize：**

- 鼠标悬停在泳道分隔线上，光标变为 resize 样式，分隔线高亮（蓝色半透明）
  - Custom 泳道垂直分隔线：`ew-resize`（↔），拖拽调整列宽
  - Participant 泳道水平分隔线：`ns-resize`（↕），拖拽调整行高
- 拖拽分隔线实时调整相邻泳道尺寸，释放后自动保存 layout
- **最小尺寸约束**：泳道缩小后的尺寸必须能包含该泳道内所有节点（节点 8px 边距），不允许缩小到无法容纳节点的程度
- 绝对最小尺寸限制为 100px（无节点时的底线）

**画布边界限制：**

- 画布不是无限平移的空白区域，其边界由泳道内容决定
- 用户拖动画布时，当触及内容的上下左右边界时停止，不允许滚动到空白区域
- 内容边界 = 所有 Custom 泳道总宽度 + 表头（32px） × 所有 Participant 泳道总行高 + 表头（32px）

**角色泳道 sticky 效果：**

- 左侧 Participant 泳道行标题（竖排标签）在垂直滚动时保持可见
- 当向下拖动画布时，行标题始终展示在最左侧，不被节点遮挡
- 行标题层 z-index 高于 ReactFlow 节点，确保始终在最前
- 标签文字随缩放比例等比例变化

**自定义泳道列标题冻结效果（Excel 冻结首行）：**

- 顶部自定义泳道列标题行（如「阶段一」「阶段二」）在垂直滚动时始终固定在画布可视区域顶部
- **垂直方向**：不随画布上下拖动移动，始终贴在容器顶部（冻结效果）
- **水平方向**：随画布左右拖动和缩放正常同步，保持与下方泳道列内容对齐
- 列标题层 z-index 高于角色泳道行标题层（z-index: 51），遮罩关系正确
- 当某列因水平滚动完全移出可视区左侧时，该列标题自然消失（overflow clip）
- 左上角固定展位空白区（行标题列头 × 列标题行头的交叉格）始终固定在左上角，与冻结列标题同层渲染
- 标签文字随缩放比例等比例变化

#### 3.5.3 节点组件

**ActionNode（活动节点）：**

```
┌─────────────────────────────┐
│                             │
│      提交订单               │  ← 仅 displayName 居中显示
│                             │
└─────────────────────────────┘
```

- **尺寸**：宽 160px，高 56px（极简设计，无顶部栏）
- **显示**：仅 `displayName` 单行居中，不展示 holder 类型、actionRef、name 等辅助信息
- **边框色**：默认 `gray-300`，选中 `blue-500`，错误 `red-400 dashed`
- **信息收敛**：节点上的所有元信息（参与者、Action 引用、I/O 等）统一在右侧属性面板查看
- **输入满足状态指示**：节点左上角显示小圆点（6px），反映该 Action 的必填输入是否被入边映射覆盖

| 状态 | 圆点颜色 | 含义 |
|------|---------|------|
| 满足 | `green-500` | 所有 required 输入均被入边映射覆盖或有 defaultValue |
| 部分满足 | `amber-500` | 部分 required 输入已被覆盖，部分未覆盖 |
| 不满足 | `red-500` | 无入边，或所有 required 输入均未被覆盖且无 defaultValue |

注意：输入满足状态仅为视觉提示，不阻止用户操作。状态在入边映射变更时实时重新计算。

**DecisionNode（决策节点）：**

```
            ◇
           / \
      支付结果  ← 仅 displayName 居中显示
           \ /
            ◇
```

- **外形**：菱形（CSS `clip-path: polygon(50% 0%, 100% 50%, 50% 100%, 0% 50%)`），尺寸 120×120px
- **显示**：仅 `displayName` 居中展示，不显示参与者标签、类型标签、name、decisionRef 或 branch 数量
- **文字**：水平展示，不被 clip-path 裁剪，多行截断（3 行）
- **Handle**：固定 4 个（上/左为 target，右/下为 source），不随分支数量变化
- **边框色**：默认 `amber-300`，选中 `amber-500`，错误 `red-400 dashed`
- **信息收敛**：分支定义、决策引用等信息统一在右侧属性面板查看

**节点选中状态：**
- 边框变为主题色（蓝色）
- 显示拖拽手柄（四角）
- 显示删除按钮（右上角，与编辑按钮并排）

**节点 hover 状态：**
- 显示编辑按钮（右上角）
- 显示连接点（上下左右四个方向的圆点）

```
│ 支付判断 │ ────────▶  │ 支付处理 │
└─────────┘   orderId  └─────────┘
              ──────▶
```

**边的路径规范：**
- 采用**正交路径（Orthogonal Path）**，连线由水平线段和垂直线段组成，拐角为 **90° 直角**
- 不使用贝塞尔曲线（Bezier）
- ReactFlow 实现：`getSmoothStepPath`（`borderRadius: 0`）

**箭头标记：**
- 连线指向 target 节点的一端必须显示**箭头标记（MarkerEnd）**
- 默认颜色 `gray-400`，选中/高亮 `blue-500`，错误 `red-400`
- 箭头大小 `8px`

**重合边跳线（Bridge）：**
- 当两条边的路径发生交叉时（一条边的水平段穿越另一条边的垂直段），在**水平段所在的边**上绘制**跳线拱形**（半圆弧形凸起，类似电路图中的 wire jump），垂直段所在的边保持直线通过
- 跳线出现位置：精确的交叉坐标点处，而非连线中点
- 跳线半径 `6px`，向上拱起（bridgeUp = true），颜色与边线一致
- 跳线归属：仅水平边绘制跳线弧形；垂直边不绘制弧形，视觉上呈现为被水平边「跨越」的直线
- 目的：避免两条边均绘制反向弧形叠合成圆圈，明确区分哪条边在「上方」跨越

**边显示元素：**
- 带箭头的正交连线
- **分支名**：从 Decision 节点创建连线并选择分支后，分支名作为 `label` 显示在连线上方
- 条件表达式（如果有）显示在连线上方（与 label 共用同一位置，`label` 优先）
- **参数标签**（受 Canvas 设置「展示行为参数」控制，默认开启）：
  - 显示位置：连线下方
  - 显示内容：该边 `mappings` 中 source 侧的输出参数**描述**列表，格式为逗号分隔的参数描述
  - 计算规则：遍历 `edge.mappings[]`，对每个映射的 `sourceField` 在源节点输出参数中查找对应的 `description`，去重后以逗号分隔显示；若 `description` 为空则回退显示参数名称（`name`）
  - Decision 边特殊规则：如果 source 为 Decision 节点，则根据 `edge.label`（分支名）定位到对应 branch 的 outputs，再取 `sourceField` 对应的输出参数描述
  - 无映射时不显示参数标签
- **完整标签组合**：上方 = `label || condition`，下方 = 参数描述列表（如 `订单ID, 金额`）
- 标签样式：上方标签（10px, 白底灰字, 边框），下方参数标签（9px, 浅灰底, 等宽字体, 与上方标签上下间距 2px）

**边选中状态：**
- 连线变为主题色（蓝色）
- 显示删除按钮（连线中点）

**映射区交互方式：**

采用「连线式」交互，用户在 source 输出字段和 target 输入字段之间拖拽建立映射关系：

1. 左侧列出 source Action 的所有 `outputs`，右侧列出 target Action 的所有 `inputs`（required 字段标记 `*`）
2. 已有映射的字段显示 `●`（实心圆点），用连线相连；未映射字段显示 `○`（空心圆点）
3. 用户从左侧 `●`/`○` 拖拽到右侧 `○`，松开后建立映射，写入 `edge.mappings`
4. 用户点击已有映射连线可删除该映射
5. 支持多源输入：一个 target 输入可被多条入边的不同 source 输出映射
6. 类型一致性提示：source 和 target 字段类型不匹配时，映射连线显示为黄色虚线，hover 提示类型不匹配警告

**映射数据结构：**

```typescript
interface EdgeMapping {
  sourceField: string;   // source Action 的输出字段名
  targetField: string;   // target Action 的输入字段名
}
// edge.mappings: EdgeMapping[]
```

**输入满足状态计算规则：**

Action 节点的输入满足状态由以下逻辑实时计算：

1. 收集该 Action 所有入边的 `mappings`，提取每个 required 输入字段被映射的来源
2. 对每个 `required: true` 的输入：
   - 若被至少一条入边映射覆盖 → 该输入「已满足」
   - 若有 `defaultValue` → 该输入「已满足」
   - 否则 → 该输入「未满足」
3. 汇总计算整体状态：
   - 所有 required 输入均已满足 → 🟢 满足
   - 部分 required 输入已满足 → 🟡 部分满足
   - 所有 required 输入均未满足 → 🔴 不满足
   - 无 required 输入 → 🟢 满足（无需外部输入）

### 3.8a 数据映射规范

**数据流模型：**

流程图中的数据传递遵循纯管道模型：

```
Action output → Edge.mappings → Action input
Action output → Edge.mappings → Decision input
DecisionBranch.outputs → Edge.mappings → Action input
DecisionBranch.outputs → Edge.mappings → Decision input
```

- 数据的唯一路径：通过 Edge 的 `mappings` 从上游输出传递到下游输入
- 无流程级变量、无全局上下文、无状态变量
- 一个 Action 有多个出边时为自然并行，每条边独立传递数据

**映射建立方式：**

| 场景 | 方式 | 说明 |
|------|------|------|
| Action → Action | 在 Edge Inspector 的映射区拖拽连线 | source output → target input |
| Action → Decision | 在 Edge Inspector 的映射区拖拽连线 | source output → Decision input |
| Decision → Action | 在 Edge Inspector 的映射区拖拽连线 | branch output → target input |
| Decision → Decision | 在 Edge Inspector 的映射区拖拽连线 | branch output → target Decision input |
| 多源输入 | 多条入边各自的 mappings 覆盖不同 target 输入 | 同一 target 输入只应被一条边映射 |

**映射约束：**

| 规则 | 说明 |
|------|------|
| 同名字段自动映射 | 创建边后，source 和 target 中 name 相同且 type 相同的字段自动建立映射 |
| 类型不匹配警告 | source 输出类型与 target 输入类型不同时，映射连线显示黄色虚线，hover 提示类型不匹配 |
| 必填输入未映射提示 | target（Action 或 Decision）中 `required: true` 且无 `defaultValue` 的输入若未被任何入边映射，在映射区标红提示 |
| 不阻止操作 | 所有映射约束均为提示性质，不阻止用户保存或连线 |

**多源输入支持：**

- 一个 Action 或 Decision 可以有多个入边，每条入边携带各自的 `mappings`
- 不同入边可以映射到 target 的不同输入字段
- 若多条入边映射到同一个 target 输入字段，后创建的映射覆盖先前的（执行时取最新值）

### 3.9 保存与验证交互

**自动保存策略（验证前置）：**

所有变更（节点位置、增删改、属性修改）均采用自动保存：

```
用户变更 → 防抖 2 秒 → 调用 validate API → 结果?
  ├── ✓ 验证通过 → 执行保存 → 显示"已保存"
  └── ✗ 验证失败 → 取消保存 → 显示错误 Banner + 高亮问题项
```

**保存状态指示器：**

| 状态 | 显示 | 说明 |
|------|------|------|
| 已保存 | `Text` (sm, muted, green) "✓ 已保存" | 所有变更已同步 |
| 保存中 | `Text` (sm, muted) "⏳ 保存中..." | 验证/保存请求进行中 |
| 验证失败 | `Text` (sm, destructive) "✗ 验证失败，未保存" | 验证未通过，数据未同步 |
| 保存失败 | `Text` (sm, destructive) "✗ 保存失败" | 网络/服务端错误 |

**验证错误展示：**

验证失败时，画布顶部显示持久性红色 Banner（不自动消失）：

```
┌─────────────────────────────────────────────────────────────┐
│ ✗ 验证失败，未保存                                          │
│ • 「node_003」孤立节点（无入边也无出边）                   │
│ • 「node_001 → node_002 → node_001」循环检测               │
│        [查看详情]  [强制保存]                                │
└─────────────────────────────────────────────────────────────┘
```

- 点击问题项自动定位到对应节点/边
- 问题节点/边高亮红色虚线边框
- 「强制保存」按钮：允许用户在知晓风险的情况下跳过验证强制保存（用于未完成的设计草稿）

### 3.10 行为定义变更的级联同步规范

当用户在流程编辑器内（通过 §3.6 或 §3.7 的新建/编辑入口）或在外部行为管理页（角色/应用/外部实体详情页）修改了某个 Action 或 Decision 的定义时，所有引用该行为的流程图数据需要做出相应联动。

#### 3.10.0 影响判断与二次确认

**影响判断时机**：用户在 `ActionFormDialog` / `DecisionFormDialog` 点击「保存/提交」时，系统在**真正写入数据库之前**，先执行影响检测。

**影响检测逻辑**：对比「当前已保存的行为定义」与「用户本次提交的新定义」，判断是否存在以下任一「破坏性变更」：

| 判断维度 | 破坏性变更条件 |
|---------|---------------|
| inputs 参数 | 有参数被删除，或参数 `name` 被修改（等同删除旧参数） |
| outputs 参数 | 有参数被删除，或参数 `name` 被修改 |
| Decision branches | 有分支被删除，或分支 `name` 被修改 |

> 仅修改 `type`、`required`、`defaultValue`、`description`、`displayName`、`logic.userDesc` 等字段**不触发二次确认**（不会导致 mappings/label 被清空）。

**存在破坏性变更时**，在 `ActionFormDialog` / `DecisionFormDialog` 保存动作执行前弹出确认 Dialog：

```
┌──────────────────────────────────────────────────────┐
│ ⚠️  此修改将影响引用该行为的流程图                     │
├──────────────────────────────────────────────────────┤
│ 以下变更将导致相关流程图的参数映射或分支绑定被清空，   │
│ 需要重新配置：                                         │
│                                                      │
│  • 删除输入参数「orderId」                             │
│    → 2 条连线的参数映射将被清空                        │
│  • 重命名分支「approved」→「passed」                  │
│    → 1 条连线的分支绑定将被清空                        │
│                                                      │
│ 确认后，受影响的流程图需重新绑定上述参数/分支。         │
│                                                      │
│              [取消]        [确认修改]                  │
└──────────────────────────────────────────────────────┘
```

**确认 Dialog 内容规则：**
- 按变更维度分组，每条变更单独列出（参数删除/重命名、分支删除/重命名）
- 同时显示该变更会影响的「连线数量」或「节点数量」（让用户明确感知影响范围）
- 若影响为 0 条（该行为未被任何流程图引用），则**跳过二次确认**，直接保存
- 点击「取消」：关闭 Dialog，回到 `ActionFormDialog` / `DecisionFormDialog`，内容保留，不执行保存
- 点击「确认修改」：执行保存 → 保存成功后立即触发级联同步（见 §3.10.1）

**外部行为管理页的二次确认：**
- 在角色/应用/外部实体详情页编辑行为时，同样执行上述影响判断和二次确认流程
- 确认弹窗提示文案追加说明：「您当前在行为管理页，修改保存后，请返回相关流程图检查并重新配置受影响的连线」
- 外部页面无法立即执行流程图级联同步，改为在用户**下次打开流程编辑器时**自动触发同步（见 §3.10.2）

#### 3.10.1 变更类型与响应规则

**A. 仅修改描述类字段（无结构变化）**

| 变更字段 | 响应 |
|---------|------|
| `logic.userDesc` / `description` | 属性面板「行为逻辑」区域实时刷新文本，无需其他操作 |
| `displayName` | 属性面板行为引用行名称实时刷新 |

**B. 输入参数（inputs）变更**

| 变更内容 | 响应 |
|---------|------|
| 新增参数 | 属性面板输入参数列表增加新行；若为 required 且无 defaultValue → 显示红色 `*` 缺少映射提示 |
| 删除参数 | **清空**所有引用该参数的 `edge.mappings`（`targetField === deletedParam.name`）；属性面板刷新后该行消失 |
| 修改参数 `name` | 等同于「删除旧参数 + 新增新参数」：清空旧 name 的 mappings，新参数以未映射状态出现 |
| 修改参数 `type` | 保留映射关系，但映射连线显示为黄色虚线（类型不匹配警告），提示用户重新确认 |
| 修改参数 `required` / `defaultValue` | 属性面板输入参数行的状态圆点和 `*` 标记实时重新计算 |

**C. 输出参数（outputs）变更**

| 变更内容 | 响应 |
|---------|------|
| 删除参数 | **清空**所有以该参数为来源的 `edge.mappings`（`sourceField === deletedParam.name`）；影响所有以该节点为 source 的出边 |
| 修改参数 `name` | 等同于「删除旧 + 新增新」：清空旧 name 的 mappings，出边参数来源更新 |
| 修改参数 `type` | 保留 mappings，出边映射连线显示黄色虚线警告 |

**D. Decision 分支（branches）变更**

| 变更内容 | 响应 |
|---------|------|
| 新增 branch | DecisionNode 出边可用 label 列表增加该分支，现有出边不受影响 |
| 删除 branch | 所有 `edge.label === deletedBranchName` 的出边：`edge.label` 清空为 `null`，边高亮红色错误状态，属性面板提示「分支已被删除，请重新选择」 |
| 修改 branch `name` | 等同于「删除旧分支 + 新增新分支」：旧 label 的出边 label 清空并报错 |
| 修改 branch 的 `outputs` | 同 C 类输出参数变更，作用于该分支 label 对应的出边 |

#### 3.10.2 触发时机

**场景一：流程编辑器内编辑（§3.7 ✏ 入口）**

编辑提交成功后，**立即**在前端内存中执行级联同步，无需刷新页面。

**场景二：外部行为管理页编辑后，打开流程编辑器**

由于 `ProcessNode.actionRef` / `decisionRef` 和 `ProcessEdge.mappings` / `label` 全部只保存**字符串引用**，不冗余行为定义的具体内容，因此：

- 流程图数据本身不会因外部编辑而「损坏」，只是字符串引用可能与行为定义的最新结构不一致
- **每次流程编辑器完成初始数据加载**（nodes + edges fetch 完毕）后，自动执行一次 `validateMappings`：
  1. 拉取所有被引用节点的最新 Action/Decision 定义（按 `holderId` 批量请求）
  2. 对比 `edge.mappings` 中的 `sourceField` / `targetField` 是否仍存在于对应 Action 的 `outputs` / `inputs` 中
  3. 对比 `edge.label` 是否仍存在于对应 Decision 的 `branches` 中
  4. 将失效项标记为橙色高亮（见 §3.10.3），**不自动清空数据**，等用户手动处理
- 这一机制天然覆盖「外部编辑后回到流程编辑器」的场景，**无需监听 `visibilitychange` / `focus` 事件**，实现更简单且可靠
- 若所有引用均合法，校验静默完成，用户无感知

#### 3.10.3 用户感知

- 级联清空的 mappings 用**橙色高亮**在属性面板和画布连线上标出（持续至用户重新绑定）
- 画布顶部显示非阻塞 Toast 提示：「行为定义已更新，部分参数映射已失效，请检查高亮的连线」
- 被清空的 edge.mappings 不自动保存，需用户重新配置后保存（防止误清空）
- **例外**：若 edge.mappings 为空（原本就没有映射），则无需任何提示

#### 3.10.4 实现复用策略

- **前端**：属性面板的输入参数 / 输出参数 / 分支列表区域均从 `actionRef` / `decisionRef` 实时 fetch 最新定义渲染（不缓存），避免数据不同步
- **映射校验**：每次属性面板打开或行为编辑提交后，执行一次 `validateMappings(edgeMappings, latestInputs, latestOutputs)` 标记失效项
- **Hook 复用**：`useRoleBehavior` / `useApplicationBehavior` / `useExternalEntityBehavior` 直接在流程编辑器的 Dialog 中调用，完整复用 CRUD 逻辑，无需重新实现

### 5.7 删除泳道

删除泳道时，因数组元素移除导致后续泳道索引前移，必须同步更新 `nodePositions` 中的索引，否则节点归属会错乱。

#### 5.7.1 删除自定义泳道

**节点处理规则：**
- 若被删泳道内有节点 → 自动迁移到相邻自定义泳道
- 相邻泳道优先级：右侧 > 左侧（若两侧都有，优先迁入右侧）
- 若只剩一个自定义泳道（即删除后为空） → 禁止删除，提示"至少保留一个自定义泳道"
- 迁移后节点的 `customLaneIndex` 更新为目标泳道的新索引
- 其他泳道内节点的 `customLaneIndex` 基于 lane ID 映射同步更新

#### 5.7.2 删除角色泳道（Participant 泳道）

**节点处理规则：**
- 角色泳道下的节点引用了该角色的 Action/Decision，删除角色泳道意味着这些引用失效
- 因此：**必须弹出二次确认 Dialog**，明确告知用户将同步删除该泳道下的所有节点
- 确认后：删除该泳道下所有节点（调用 nodes API 扠除），同步移除 `nodePositions` 中对应条目
- 其他泳道内节点的 `participantLaneIndex` 基于 participantId 映射同步更新

**二次确认 Dialog：**

```
┌─────────────────────────────────────┐
│ 删除角色泳道              [×]   │
├─────────────────────────────────────┤
│ ⚠️ 确定要删除「客户」角色泳道吗？  │
│                                     │
│ 该泳道下有 3 个节点，删除后这些   │
│ 节点及其引用的 Action 将一并移除， │
│ 无法恢复。                          │
│                                     │
│        [取消]  [确认删除]           │
└─────────────────────────────────────┘
```

**校验规则：**
- 若只剩一个角色泳道 → 禁止删除，提示"至少保留一个角色泳道"

## 8. 错误处理

| 场景 | 处理方式 |
|------|---------|
| API 请求失败 | Toast 提示错误信息，操作按钮恢复可用状态 |
| 节点创建失败 | 节点从画布移除（回滚），显示错误 Toast |
| 边创建失败（如形成环） | 边从画布移除，显示错误 Toast "此连接将形成循环" |
| 保存失败 | 保存按钮变为"保存失败，重试"，数据不丢失（本地缓存） |
| 验证失败 | 画布顶部显示错误 Banner，问题项高亮 |
| 跨泳道嫁接失败 | Dialog 保持打开，显示错误信息，用户可选择"仅移动节点" |
