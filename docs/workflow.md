# 系统使用工作流

> 本文档独立管理 ai-prototype-manager 系统的完整使用工作流。
> 工作流内容会随着系统建设持续补充和迭代。
>
> 最后更新：2026-04-27

---

## 完整工作流：A → F 六阶段

> 本系统不仅是原型设计工具，更是**产品定义的单一事实来源（Single Source of Truth）**。
> PM 通过本系统完成从业务理解到产品定义的全过程，产出物向下连接研发实现和测试验证。

---

### 阶段 A：理解业务

#### Step 1: 项目初始化
PM 定义：
- 项目目标和范围
- 目标用户/设备/场景
- 约束条件（技术/业务/合规）

**产出**：`Project.meta`

**详细规格**：待补充

#### Step 2: 领域建模
PM + AI 协作识别：
- 业务领域中的实体（Entity）
- 实体间的关系（Relation）
- 实体的行为声明（Behavior）
- 字段定义与约束

**产出**：`domainModels[]`

**详细规格**：待补充

---

### 阶段 B：定义系统如何运转 ⭐ 核心新增阶段

#### Step 3: 业务流程设计
PM + AI 梳理本系统的核心业务流程：

**梳理问题：**
- 本系统有哪些核心业务流程？
- 每个流程的触发条件是什么？
  - 人工触发（PM/操作员手动启动）
  - 时间触发（定时任务、周期性执行、延时）
  - 事件/信号触发（传感器数据、外部消息、数据变化、规则满足）
  - 流程间调用（一个流程步骤触发子流程）
- 流程包含哪些步骤？步骤间关系？（DAG + 有限循环）
- 哪些步骤需要人参与？→ 关联到 UI 页面
- 哪些步骤是自动的？→ 调用 API / 执行规则 / 设备交互
- 流程之间如何协作？

**产出**：`businessProcesses[]`

**详细规格**：详见 `docs/08-business-process.md`（设计完成后链接）

---

### 阶段 C：定义人机接口

#### Step 4: 应用框架规划
基于「领域模型」+「业务流程」，规划应用结构：

- 需要哪些 Application？（Web / iOS / Android / 工业终端 / ...）
- 每个 App 下需要哪些 Page？
- 每个 Page 对应流程中的哪些人工任务节点？
- 还有哪些页面是流程之外的独立交互页面？

**产出**：`applications[].pages[]`（组件树 + zones[] + layoutHint）

**详细规格**：待补充

#### Step 5: 页面细节设计
每个 Page 内部：

- 有哪些组件？属性和层级关系？
- 组件有哪些交互逻辑？（hooks / lifeCycles）
- 数据绑定到哪些字段？
- 权限控制？

**产出**：完整的 Component 树 + props + hooks + bindings

**详细规格**：待补充

---

### 阶段 D：视觉与验证

#### Step 6: 导出 → 设计工具 → 导入
- 导出设计骨架给第三方设计工具
- 第三方工具产出高保真设计稿（HTML / 图片）
- PM 导入高保真产物
- AI 识别区域，建立与组件树的映射锚点
- 校验布局意图是否被遵循

**产出**：`designArtifacts[]` + `Component.layout`

**详细规格**：详见 `docs/06-external-design-integration.md`

#### Step 7: 运行与验证
两种运行模式：

- **原型介绍模式**（主模式）：逻辑说明 + 元数据编辑，不运行原型
- **原型演练模式**（辅助模式）：高保真界面 + 可交互 Mock 运行

**详细规格**：待补充（介绍模式 UI 布局延后讨论）

---

### 阶段 E：与研发系统集成 ⭐ 新增

#### Step 8: 研发规格输出
本系统通过 MCP/API 向研发侧输出完整的产品实现规格：

| 输出维度 | 内容 | 下游消费者 |
|---------|------|-----------|
| **前端功能规格** | 页面结构 / 组件清单 / 交互逻辑 / 数据绑定 / 状态管理 | Coding AI / 前端开发 |
| **后端功能规格** | API 接口定义 / 业务流程实现逻辑 / 数据处理 / 权限控制 | Coding AI / 后端开发 |
| **设备交互规格** | 设备协议 / 信号定义 / 控制逻辑 / 异常处理 | 嵌入式 / IoT 开发 |

**未来能力 — 实现对照检查：**
- 研发完成后，系统可检查实现是否覆盖了原型的所有能力
- 对照维度：API 完整性 / 流程覆盖度 / 交互完整性 / 规则实现度

**详细规格**：待补充

### 阶段 F：与测试系统集成 ⭐ 新增

#### Step 9: 测试用例生成
本系统中定义的结构化信息可作为测试系统的优质输入来源：

| 来源 | 自动生成的测试类型 | 示例 |
|------|-------------------|------|
| `businessProcesses[]` | 端到端测试场景 | 「订单创建→支付→发货→签收」全流程测试 |
| 组件 `hooks[]` | 交互测试用例 | 点击提交按钮 → 触发校验 → 调用 API → 处理响应 |
| 权限注解 `permissions[]` | 权限测试矩阵 | admin/editor/viewer 三角色 × 各操作权限组合 |
| 校验规则 `constraints` | 输入边界测试 | 必填项为空 / 超长输入 / 格式非法 / 边界值 |
| 业务流程分支 `conditions` | 分支覆盖率测试 | 正常路径 + 各异常分支路径 |

**详细规格**：待补充
