## 二、问题清单与根因分析

### 问题 1：PRD 异常场景在 API 层漏覆盖（C-1）

**现象**: PRD §4.1.4.7 定义了 5 个异常场景，其中"网络错误"和"服务端 500"只有 E2E 用例没有 API 用例。

**根因**:
- 写 E2E 时自然覆盖了网络/服务端异常的 UI 表现（Error Boundary、重试按钮），误以为这已足够
- 遗漏了规范中的硬性要求：**"每条异常场景至少有 1 个 API 用例"**（test-convention §6.1）
- API 层和网络层是不同的测试关注点：API 测试验证的是**错误响应格式是否符合统一错误码体系（G-M1-10）**，E2E 测试验证的是**前端如何展示错误**

**影响范围**: 如果只写 E2E 不写 API，AI 编码时可能不实现后端的错误格式标准化（error code / message 结构），导致前端解析出错

---

### 问题 2：AC 引用语义错配（C-2）

**现象**: TC-E2E-M1-01-010（归档项目视觉区分）引用了 AC-M1-24（角色权限控制：Developer 隐藏写按钮）。

**根因**:
- 编写时看到编号中有 "M1-24" 就直接引用了，**没有核对 AC 的实际内容**
- AC-M1-24 描述的是"Developer/Tester 用户看不到写按钮"，而该用例测试的是"归档行视觉样式差异"
- 两者完全无关：一个是**角色维度的权限**，一个是**状态维度的 UI 样式**

**影响范围**: 覆盖矩阵会误导后续审核者认为"角色权限已在 F-M1-01 验证过"，实际上 F-M1-01 根本不涉及角色权限（那是 §5.4 的内容）

---

### 问题 3：业务规则覆盖归属错误（C-3）

**现象**: B-M1-09（归档后 UI 反馈：Toast + 列表行为）被标给了纯 API 用例 TC-API-M1-01-007。

**根因**:
- B-M1-09 的关键词是"UI 反馈""Toast""列表移除"——这些都是**浏览器端行为**
- API 用例只能验证 HTTP 响应和 DB 状态变化，无法验证 Toast 是否弹出、列表行是否消失
- 编写覆盖矩阵时**从 PRD 文本复制了规则名到最近的用例上**，没有判断该用例的能力边界

**影响范围**: 如果 AI 编码时只看 API 用例来实现 B-M1-09，会遗漏 Toast 提示和列表联动刷新逻辑

---

### 问题 4：跨功能点用例放置模糊（I-1/I-2）

**现象**: 恢复项目（TC-API-M1-01-018）和无效状态转换（TC-API-M1-01-019）属于 F-M1-05 的领域但放在了 F-M1-01 中。

**根因**:
- 恢复操作和归档操作使用同一个 `PATCH /projects/:id/status` 端点，从"端点归属"角度觉得放哪里都可以
- 但从**功能点职责**角度：恢复是 F-M1-05（归档/恢复）的核心功能，不是 F-M1-01（列表）的功能
- 缺少明确的"跨功能点标注规范"——什么情况下允许跨功能点放、必须标注什么

**影响范围**: 后续编写 F-M1-05 时可能重复编写相同用例，或遗漏因为"以为在 01 里写过了"

---

### 问题 5：参数校验遗漏（I-3/I-4）

**现象**: pageSize 和 order 参数的非法值校验没有用例，虽然 sort 和 status 和 page 都有。

**根因**:
- PRD §4.1.4.6 校验规则汇总表列出了 **6 个参数**（search/status/page/pageSize/sort/order）
- 写用例时按"业务重要性"选了几个重点参数来校验，没有**逐项勾选**
- page=0 是因为它是常见的边界值（0 是整数下界）才被选中；pageSize 和 order 因为"不太容易出错"而被跳过

**影响范围**: AI 编码时如果 TypeBox schema 对这两个参数漏了枚举约束，不会有测试用例拦截

---

### 问题 6：Skeleton 加载态缺失（I-5）

**现象**: PRD 明确要求 Skeleton 加载态（§4.1.3 步骤 1 和 §4.1.2 元素清单），但所有 E2E 用例都从"页面已加载"开始。

**根因**:
- E2E 用例的前置条件统一写了"等待页面加载完成（Skeleton 消失）"，把 Skeleton 当成了**前置条件的过渡态**而非**需要验证的目标**
- PRD 把 Skeleton 写在了交互流程的步骤 1（"显示 Skeleton 加载状态"），但没有单独列为一个 AC，导致按 AC 勾选时漏掉

**影响范围**: AI 编码时可能跳过 Skeleton 组件实现，或实现后加载体验差（白屏闪烁 → 数据突然出现）

## 三、规避方案（写入 checklist 供后续参考）

### 规则 R-TC-01：异常场景必须双层覆盖

**触发条件**: 每次编写涉及异常场景的测试用例时

**规则内容**:
- PRD 中定义的每个异常场景，**必须同时有 API 层和 E2E 层的用例**（除非该场景仅存在于某一层）
- API 层关注：错误码格式、HTTP 状态码、响应结构是否符合 G-M1-10 统一体系
- E2E 层关注：用户看到的提示文案、重试机制、数据保留
- 两层的断言目标不同，不可互相替代

**检查方式**: 写完异常场景用例后，对照 PRD 异常场景汇总表逐行打勾：

```
□ 异常场景 #1: [ ] API 用例 [ ] E2E 用例
□ 异常场景 #2: [ ] API 用例 [ ] E2E 用例
...
```

---

### 规则 R-TC-02：AC 引用必须核对内容语义

**触发条件**: 每次在「对应AC」字段填写 AC 编号时

**规则内容**:
- **禁止仅凭编号匹配就引用 AC**。必须打开 PRD 核对 AC 的 Given-When-Then 内容是否与当前用例的实际验证目标一致
- 特别注意编号相近但含义不同的 AC（如 AC-M1-14 vs AC-M1-24）
- 如果一条用例覆盖了多个 AC，逐一核对每个 AC 的语义都与用例相关

**防错手段**: 在覆盖矩阵中增加一列「AC 语义简述」，强制自己写出理解

---

### 规则 R-TC-03：B 规则归属必须匹配用例能力边界

**触发条件**: 每次在覆盖矩阵中将 B/G 规则映射到 TC 时

**规则内容**:
- 判断该规则描述的行为是**数据层行为**还是 **UI 层行为**：
  - 涉及 DB 状态变更、HTTP 响应格式 → 应由 API 用例覆盖
  - 涉及 Toast、弹窗、列表刷新、视觉样式 → 应由 E2E 用例覆盖
  - 涉及两者（如归档：状态变更 + Toast）→ API 覆盖数据部分，E2E 覆盖 UI 部分
- 纯 API 用例不能声称覆盖包含 "UI""视觉""Toast""列表行为" 关键词的业务规则

---

### 规则 R-TC-04：跨功能点用例必须显式标注

**触发条件**: 当一个用例测试的功能不属于当前功能点的核心职责时

**规则内容**:
- 在用例的「对应AC」或「备注」字段中标注：`（跨功能点：源自 F-Mx-NN）`
- 在覆盖矩阵中也标注来源
- 判断标准：如果该功能的**完整主流程定义在另一个功能点的 PRD 章节**中，则为跨功能点
- 跨功能点用例允许存在（避免重复），但必须标注清楚，方便后续合并或去重

---

### 规则 R-TC-05：参数校验必须逐参数全覆盖

**触发条件**: 每次编写含查询参数的 API 的测试用例时

**规则内容**:
- 取 PRD 中的「校验规则汇总表」或「数据规格」中的输入参数表
- **逐行遍历每个参数**，为每个参数至少写 1 条非法值用例：
  - 枚举类型 → 传一个不在枚举列表中的值
  - 数值边界 → 传下界-1、上界+1、0、负数
  - 字符串长度 → 传空串、超长串、特殊字符
  - 必填/可选 → 缺失必填项、传入多余字段
- 使用清单打勾法，不要凭感觉挑选"重要的"来校验

---

### 规则 R-TC-06：加载态是独立验证目标，不是前置条件

**触发条件**: 编写任何涉及页面加载的 E2E 用例时

**规则内容**:
- 区分两种"加载"：
  - **前置条件中的加载**："等待页面加载完成"—— 这是用例的起点，不需要验证加载过程本身
  - **待验证的加载态**：Skeleton / Spinner / 遮罩 —— 这是 PRD 明确要求的 UI 行为，必须有专门用例验证
- 判断标准：如果 PRD 的元素清单或交互流程中明确提到了某种加载态组件名称（如"Skeleton"），则它是一个独立的验证目标
- 即使没有对应 AC，也应在 E2E 中补充加载态用例（标记为"补充覆盖"）

## 四、本次 Review 整体评估

### 做得好的地方

1. **模板遵循度高**: 公共上下文、正常/异常分组、字段完整性、断言粒度都严格符合 test-convention.md v1.0
2. **API 断言质量好**: TC-API-M1-01-001 作为首条用例，关键字段断言 + 否定断言（description/config 不存在）+ 后置验证，树立了好的模板
3. **E2E 可执行性强**: 操作步骤具体到按钮颜色、弹窗文案、Badge 样式，AI 或 QA 可直接执行
4. **主动超出最小要求**: 并发归档（017）、状态转换拒绝（019）、搜索超长（008）等都是 PRD 未强制但应该测的场景
5. **设计决策标注诚实**: 对不确定的实现方案（page=0 处理、并发幂等行为）明确标注"待确认"

### 需要改进的模式

1. **先写覆盖矩阵再写用例**: 当前是写完用例再填覆盖矩阵，容易遗漏。应改为：先从 PRD 提取全部 B/G/AC/异常清单作为骨架矩阵，写完每个用例后立即勾选
2. **AC 核对应该是强制性步骤**: 不是"记得就核"，而是每填一次对应AC 字段都必须打开 PRD 确认
3. **API/E2E 分工意识需加强**: 写每个用例前先问自己"这个行为是在 HTTP 层还是在浏览器层？"再决定放在哪个文件里
