## 1. 项目定位

### 一句话定位
在 AI 时代，**面向 AI 的软件产品定义与生命周期管理平台**——以结构化语义原型为核心，连接产品定义、研发实现与测试验证。

### 核心定位演进

**初版定位（聚焦原型设计）：**
传统原型工具（Figma/Sketch 等）聚焦于"给人看的高保真视觉"——布局、样式、展示效果。但真正构建可用软件系统的关键信息（业务逻辑、交互逻辑、数据关系）在这些产物中会丢失，导致 Coding Agent 无法还原设计者的意图。

**当前定位（产品生命周期中枢）：**
本系统不仅是原型设计工具，更是 **「产品定义的单一事实来源（Single Source of Truth）」**。它承载完整的产品语义信息，向下连接研发实现和测试验证：

```
PM 设计产品定义（完整语义）
  │
  ├─→ 阶段 D：给 PM 自己看（原型介绍 / 演练验证）
  │
  ├─→ 阶段 E：给研发 / Coding AI（指导前端+后端+设备交互的实现 + 实现对照检查）
  │
  └─→ 阶段 F：给测试系统（从流程/交互/规则自动生成测试用例）
```

本项目聚焦于 **"给 AI 用的结构化语义"** —— 确保这些关键信息能够完整传递给所有下游消费者。

## 2. 五大核心支柱

### 支柱一：Agentic 原型构建
- 产品经理与 AI 对话协作完成产品定义（含原型）
- PM 输出**决策和思考**，AI **动笔执行**
- 支持**从粗到细的全流程**：
  - 粗粒度：PM 说"我要一个工业控制系统" → AI 生成完整定义 → PM 审核修改
  - 细粒度：组件/步骤/字段级对话迭代
- 人类可**实时观察** AI 的产出进程和结果

### 支柱二：结构化语义数据
超越布局和展示层面的"高保真"，最大化抽象和提取产品定义中的六类信息（按优先级排序）：

| 优先级 | 信息类型 | 具体内容 |
|--------|---------|---------|
| 1（最高） | **业务流程** | 端到端业务流程编排（触发→步骤→分支→参与者→异常处理） |
| 2 | 交互逻辑 | 人机交互（点击、跳转、状态变化、条件分支） |
| 3 | 数据模型关系 | 领域实体、UI 元素绑定字段、数据流向 |
| 4 | 业务规则 | 校验逻辑、权限控制、计算公式 |
| 5 | 设备交互 | 传感器/执行器通信协议、信号定义、控制逻辑 |
| 6 | 组件语义 | 元素的业务意图（是"提交"还是"取消"） |

> ⚠️ 注意：**业务流程**提升为最高优先级信息类型——它是系统的运转骨架，其他所有信息都围绕它组织。

### 支柱三：Agentic 数据输出（面向研发）
- 面向 Coding AI / 研发人员提供易于提取、理解的完整产品规格
- 输出内容包括：
  - 前端功能规格（页面/组件/交互逻辑/数据绑定）
  - 后端功能规格（API 接口/业务流程/数据处理逻辑）
  - 设备交互规格（设备协议/信号定义/控制逻辑）
- 未来支持：实现对照检查——研发完成后验证是否覆盖了原型的所有能力

### 支柱四：Agentic 数据输出（面向测试）
- 面向测试系统提供结构化的测试用例输入来源
- 自动生成能力：
  - 从业务流程 → 端到端测试场景
  - 从组件 hooks → 交互测试用例
  - 从权限注解 → 权限测试矩阵
  - 从校验规则 → 输入边界测试用例

### 支柱五：外部设计稿集成
- 视觉呈现委托给第三方专业工具（Figma/v0/Cursor 等）
- 本系统专注语义/逻辑管理，通过 layout 锚点与外部设计稿关联
- 支持导入高保真产物 + AI 映射 + 布局意图校验

## 3. 协作模式与链路

### 3.1 完整生态链路

```
PM（产品经理）
  │  对话 + 决策
  ▼
Design AI（本系统集成 LLM 能力）
  │  动手执行：定义领域模型、设计业务流程、规划应用框架、
  │           细化页面组件、定义交互逻辑
  ▼
产品定义产物（完整语义数据 + 外部设计稿关联）
  │
  ├───────────────────┬───────────────────┐
  ▼                   ▼                   ▼
PM 自用              研发 / Coding AI     测试系统
(介绍/演练模式)      (MCP 只读接口)       (MCP 输出接口)
  │                   │                   │
  ▼                   ▼                   ▼
验证设计             指导编码            生成测试用例
                     实现对照检查
  ▼
可用软件系统
```

### 3.2 接口方向

| 方向 | 角色 | 性质 | 消费者 |
|------|------|------|--------|
| **上游**（创建时） | Design AI 通过 MCP 操作原型 | 读写接口 | Design AI |
| **下游-研发**（编码时） | Coding AI 通过 MCP 读取完整产品规格 | **只读查询** | Coding AI / 研发人员 |
| **下游-测试**（测试时） | 测试系统通过 MCP 获取测试输入 | **只读输出** | 测试平台 / 测试 AI |

## 4. 技术架构决策

### 技术栈
- **B/S 架构**，Node.js 技术栈
- 不考虑对标或兼容 Figma/Sketch

### 原型产物格式
- 视觉层：**HTML + CSS + JS**（页面布局、样式呈现）
- 选择 HTML 的原因：大多数 AI 都很容易生成格式完整的 HTML
- 数据库需要保存生成好的 HTML

### 原型产物数据模型 — 双轨制（已确定）

**核心决策：视觉层与语义层分离**

| 层 | 格式 | 职责 |
|---|---|---|
| 视觉层 | HTML + CSS | 页面布局、样式呈现 |
| 语义层 | JS（内聚引用） | 交互逻辑、数据绑定、业务规则、组件语义 |

- HTML 通过 `<script>` 标签引用语义层 JS 文件
- 两者在数据库中关联存储，导出时保持引用关系
- **不是**把所有信息塞进一个自包含 HTML 文件里，而是保持分离但可引用的关系

### MCP 接口设计（双向）

| 方向 | 角色 | 性质 | 状态 |
|---|---|---|---|
| 上游（创建时） | Design AI 通过 MCP 操作原型 | 读写接口 | 形态待定（CRUD vs 意图式） |
| 下游（编码时） | Coding AI 通过 MCP 读取原型 | **只读查询** | 明确为只读 |

- 下游接口用途：获取项目的完整页面结构和交互逻辑
- 上游接口形态尚未确定，需在系统设计阶段讨论

## 5. 核心交互机制：完整性框架驱动问答

### 5.1 核心理念
本系统的一个关键特征：**AI 被一个「原型完整性框架」约束，必须按照框架逐项确认原型的每个要素，不能猜测或跳过。**

这与当前大多数 AI 工具的模式形成鲜明对比——现有 AI 倾向于"大胆假设、静默填充"，产物看起来完整但充满臆测。本系统强迫 AI **不断思考、主动提问、获得决策**，确保原型是 **100% 自洽且逻辑完备**的。

### 5.2 完整性框架的设计

| 决策项 | 结论 |
|--------|------|
| **框架来源** | 系统预定义一套通用的**「软件产品原型要素清单」**，所有项目走这套标准流程 |
| **框架演进** | 这套标准可以在系统中**不断迭代和完善**，不是一成不变的 |
| **覆盖范围** | **三层全覆盖**：<br>1. 原型内部自洽（页面跳转不矛盾、状态机完备）<br>2. 原型与需求对齐（功能无遗漏）<br>3. 技术可行性（描述的内容实际可编码实现） |

### 5.3 提问机制

| 决策项 | 结论 |
|--------|------|
| **触发策略** | **主动式（问卷模式）**：AI 先扫描完整性框架，一次性列出所有缺失项，像结构化问卷一样逐个确认 |
| **PM 交互自由度** | **可主动打断**：PM 可以随时打断 AI（"先别问那个了，这块我先这样定"），引导对话方向 |

### 5.4 这个机制的意义
- **防止 AI 臆测**：每个设计决策都来自 PM 的明确输入，而非 AI 的"合理猜测"
- **保证原型质量**：框架确保不会遗漏关键维度
- **提升下游编码质量**：自洽的原型 → Coding Agent 能更准确地还原设计意图
- **框架可持续进化**：随着使用积累，要素清单可以越来越完善

## 6. 产品原型要素清单 — 讨论结论

> 基于行业资料（NNGroup 原型规范框架等）整理出 23 个要素条目，按六大类逐项深入讨论后得出以下结论。
> 讨论过程中浮现了多个重要的架构发现（标记为 ⭐）。

### 6.1 页面/屏幕结构层

| # | 要素 | 结论 |
|---|------|------|
| 1 | 页面清单与层级关系 | 系统自动维护页面清单及树形层级结构 |
| 2 | 页面布局结构 | 用 JSON Schema 声明式描述布局区域划分（header/sidebar/main/footer 等） |
| 3 | 导航与路由 | 归入交互逻辑层，以「跳转动作」统一表达 |
| 4 | 响应式/适配策略 | 初期不考虑，聚焦单一目标平台 |

### 6.2 组件/元素层

| # | 要素 | 结论 |
|---|------|------|
| 5 | 组件类型分类 | 需要标准组件库，AI 只能使用预定义组件类型来构建页面 |
| 6 | 组件属性规格 | 每种组件有预定义属性 Schema；**AI 先智能填充，不确定项再问 PM** |
| 7 | 组件状态定义 | 预定义状态集 + AI 按业务场景选择适用状态 + **支持动态扩展** |
| 8 | 组件间约束关系 | 通过**对象生命周期事件钩子**定义判断逻辑和控制行为 |

### 6.3 交互逻辑层（优先级最高）

| # | 要素 | 结论 |
|---|------|------|
| 9 | 用户操作→系统响应映射 | 在对象 Schema 树中，通过**生命周期钩子**用 JSON 表达事件信息和对应的 action 行为 |
| 10 | 页面跳转流程图 | 不单独维护，从所有 action 记录中**自动聚合生成** |
| 11 | 表单提交流程 | 通过**表单组件的生命周期事件钩子**统一表达（校验→提交→成功/失败回调） |
| 12 | 条件分支逻辑 | 使用 **JSON 条件语法** `{ if, then, else }`，易读且易解析 |
| 13 | 模态/弹窗/抽屉 | 建模为**覆盖层组件**，有独立生命周期；按作用域分级挂载（页面级 vs 系统级/App 级） |

### 6.4 数据模型层

| # | 要素 | 结论 |
|---|------|------|
| 14 | 实体与字段定义 | ⭐ 每个 App 项目维护独立的**数据模型**（实体+字段），所有原型共享引用；UI 组件绑定到数据模型字段；⭐ 需新增**「领域模型管理」功能**，数据模型可从领域模型细化而来 |
| 15 | UI↔数据字段绑定 | **声明式绑定路径**，如 `{ binding: "User.name" }`，指向数据模型中的字段 |
| 16 | 数据流向 | ⭐ **系统自动扫描推导**（非人工标注）：系统在 App 级别扫描整个原型 Schema，分析所有读写操作，自动生成每个字段的 source/destination 元数据写入数据模型 JSON；PM 可为字段添加文本备注 |
| 17 | 列表控制参数 | 分页/排序/筛选作为 **Table/List 组件的属性**管理 |

### 6.5 业务规则层

| # | 要素 | 结论 |
|---|------|------|
| 18 | 输入校验规则 | **JSON Schema 风格**声明（required / pattern / min / max 等） |
| 19 | 权限与角色控制 | 声明式权限注解 `{ visible: ["admin"], editable: ["admin"] }`；⭐ App 级需有**角色/用户管理**功能，组件中的角色名从预定角色列表中选择 |
| 20 | 业务计算公式 | ⭐ **不是页面级属性，而是 App 级别的「业务规则」节点**，按业务域组织；页面动作通过引用使用规则；格式 `{ formula: "price * quantity" }`；PM 自然语言描述 → AI 转 JSON → MCP 输出给 Coding AI；**待后续深入设计** |
| 21 | 异常处理策略 | 分两层：前端交互异常在页面对象 action 的 `onError` 回调中定义；后台/批处理/API 异常在对应**任务对象**的行为定义中（JSON 格式）；⭐ 各类对象应有 App 级专属子节点 |

### 6.6 内容层

| # | 要素 | 结论 |
|---|------|------|
| 22 | 文案与标签 | AI 智能生成默认文案 + PM 可随时修改；注意：独立文本（如 Label）是**单独的组件节点**，非其他组件的属性 |
| 23 | 示例/占位数据 | 分两类：**业务数据**由系统从 App 数据模型自动生成示例副本并打包进原型输出物；**组件自身数据**（如 placeholder）存于组件内部 Schema |

### 6.7 讨论中浮现的关键架构发现汇总

本次要素清单讨论中，除了各要素本身的结论外，还浮现出了以下几个跨要素的**关键架构发现**：

#### 发现一：App 级共享资源体系
原型不是孤立存在的——每个 App（项目）拥有一组**共享基础设施**，所有原型从中引用：

| App 级资源 | 职责 | 原型中的使用方式 |
|-----------|------|-----------------|
| **数据模型** | 实体定义 + 字段定义 + 自动推导的数据流向元数据 | UI 组件通过 binding 路径引用字段 |
| **领域模型** | 业务概念抽象（可细化为数据模型） | 作为数据模型的来源 |
| **角色与用户** | 预定义角色列表和用户 | 权限注解中的角色名从此选择 |
| **业务规则** | 计算公式、业务逻辑，按业务域组织 | 页面 action 引用规则 ID |
| **任务/批处理/API 对象** | 后台行为定义 | 异常处理等在此定义 |

#### 发现二：统一的「对象生命周期」交互范式
贯穿组件、页面、弹窗、表单等各类对象的统一交互表达模式：
- 每个对象有**生命周期**（创建→渲染→交互→销毁）
- 交互逻辑通过**生命周期钩子**用 JSON 表达
- 约束/联动关系也在钩子中定义判断逻辑和控制行为
- 这套范式将取代分散的、各自为战的交互描述方式

#### 发现三：自动化推导能力
系统不只是被动的记录工具，还具备主动的分析能力：
- **数据流向**：扫描原型 Schema → 自动推导字段的 source/destination
- **流程图**：聚合所有 action 记录 → 自动生成完整跳转流程
- **示例数据**：根据数据模型 → 自动生成 mock 数据副本
