## 议题：subProcess 完整设计

### Q1: subProcess 的本质是什么？

**PM 选择：Process 层面的父子关系**

> subProcess 本质上是一个 Process 对象的属性（如 parentProcessId + childProcessIds[]），而不是节点层面的概念。通过 Process 间的父子关系来表达嵌套。底层的全局原子节点池里不意识到 process 的存在。

**PM 详细描述渲染逻辑**：
> 1. Process A 里包含的内部所有原子节点（行动，边，Decision）信息，假设 100 个
> 2. Process A 层面关注（创建/拥有）的其他流程对象 ID——流程 B（流程 B 因为被本 process A 关注，且在其内部拥有的底层节点数上也一定是 A 的节点的子集）的清单
> 3. 流程渲染界面首先渲染流程 A 内部、不属于任何一个其他流程的节点（直接在泳道里渲染节点、边），然后渲染 A 关注的其他流程（B/C...）的节点，这些子流程节点内的实际元素被隐藏（不渲染），用户可点击子流程卡片的查看详细按钮，则递归进入子流程的渲染视图

**核心结论：不需要 CallNode 等新节点类型**

---

### Q2: 数据如何跨流程边界传递？

**PM 选择：复用已有边的 mappings（推荐）**
> 通过边自然传递。父流程中进入子流程前的最后一个节点有边连接到子流程的 entryNodeId，子流程出口节点有边连接到父流程中离开子流程后的第一个节点。这些边已经在全局边池中存在，mappings 已经定义好了。不需要额外的 inputMapping/outputMapping。

---

### Q3: 同步 vs 异步执行？

**PM 详细回答（重要洞察）**：

> 流程图本身的 edge 只表达有方向的、同步的信息传递+时间延续，本身不存在异步概念。所谓的「异步」，其实就是一个 Action 节点可以有多个输出边 edges，那么这多个边、以及其后续的所有活动，自然就是并行进行的

**核心结论：Edge = 同步信息传递 + 时间延续；并行性来自 fan-out 拓扑；无显式异步原语**

---

### Q4: 超时机制？

**PM 选择：暂不考虑（推荐）**
> 当前阶段只关注「定义」，不涉及运行时执行。超时是运行时引擎的事，不在 Process 定义层考虑。如果一定要表达，也可以借助对象的 decision 来定义一个判断分支来表达是否超时的后续处理行为

---

### Q5: 失败/异常处理？

**PM 选择：完全不在定义层考虑异常**
> 异常处理是运行时引擎和编码阶段的事。如果一定要表达，也可以借助对象的 decision 来定义一个判断分支来表达处理异常的后续行为

**一致模式**：超时和异常都通过 Decision 分支建模（如：「成功」/「超时」/「失败需重试」）

### Q10: 节点归属约束？

**PM 详细回答（重要洞察）**：

> 1. 本质上子流程也是流程，内部包含了若干节点和边，他们是可以重叠的
> 2. 但是，如果有多个子流程要被同一个流程关注（并且在这个上层流程里展示），则他们不能有重叠，因为重叠的话，在上层流程的视角来看，因为所有的边都是由最底层的原子池保存并呈现的，则会在视觉呈现上产生矛盾（一个行为以及它的边不可能同时指向两个子流程容器卡片）
> 3. 所以可能在流程被纳入其他流程的时候要做严格的检查。同时流程渲染的时候本身也要检查自己关心的其他流程（子流程）是否有交叉的节点

**两层约束**：
- **子集约束**：Child.nodeIds ⊆ Parent.nodeIds
- **兄弟互斥**：同父流程下的 Child_i ∩ Child_j = ∅
- 独立流程之间可以任意重叠（不在同一视图中展示）

## 议题：循环约束规则

### Q1: 是否允许循环？

**PM 选择：倾向于允许循环，探讨问题**
> PM 想了解允许循环会有什么问题

**AI 分析了四个维度的影响**：
1. 渲染层面 — 影响较小，布局算法有成熟方案
2. 数据流层面 — 需要明确回边数据语义
3. 执行语义 — 核心问题是区分合法有限循环 vs 意外无限循环
4. 子流程嵌套 + 循环 — 复杂度叠加

### Q2: 循环边是否允许跨越子流程边界？

**PM 选择：软限制 + 强警告**
> 允许跨子流程回边，但给出强警告提示。

### Q3: 如何防止无限循环？

**PM 选择：静态分析 + 警告（推荐）**
> 不强制阻止 PM 画循环。但在完整性校验时分析每个循环是否至少有一条出口路径。如果没有出口则标记为「潜在死循环」并警告。不做硬性阻断。

### Q4: 回边的数据语义？

**PM 详细回答（三点重要洞察）**：

1. **回边也是普通的边**，遵循关于 edge 的所有定义，要携带数据，且数据要符合 target 对应 Action 的参数要求
2. **Decision 作为行为也可以产生输出信息**——不同 branch 允许输出不同的参数，这些参数可以由出去的 edge 携带。（确认 v1.1 的 DecisionBranch.outputs 模型已足够）
3. **审批打回的设计模式建议**：把「合同创建」与「合同修改」作为 2 个独立的行为节点，因为这两个活动需要的输入差异很大。当审批不通过时，应该回到「合同修改」节点（传入合同ID、审批意见），而不是直接回到「合同创建」

**关于 Decision 输出的确认**：
> 现有模型已足够（推荐）。v1.1 的 DecisionBranch.outputs 已支持不同分支有不同 outputs。

### Q5: 循环完整性校验规则？

**PM 选择：三项全做（推荐）**
> (1) 循环出口检测 (2) 回边数据合规性 (3) 跨子流程警告。作为 AI 辅助能力中「完整性校验」的一部分。

## 第三部分：技术栈选型

### 选型维度（PM 定义）
PM 明确要求从三个维度分析：
1. 市场上相关框架的生态完整度、框架能力、未来发展潜力
2. 我们项目的定位、5 个阶段规划要实现的能力
3. 最后才是个人偏好

### 最终决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 后端框架 | **Fastify** | 生态好、性能优秀、插件体系成熟、与 TypeScript 深度集成 |
| 数据库 | **PostgreSQL** | 关系型、JSON 支持、生态成熟、适合复杂查询 |
| ORM | **Drizzle** | 类型安全、SQL-like API、轻量、与 TypeBox 天然配合 |
| 项目结构 | **Monorepo (pnpm workspaces + Turborepo)** | 多包共享类型、统一构建、适合前后端分离 |
| 前端 | **React + Vite + TypeScript** | 生态成熟、开发体验好、与后端共享类型 |
| 校验方案 | **TypeBox + Ajv** | 一套定义三处复用（TS 类型 + 运行校验 + JSON Schema 输出） |

## 第四部分：MVP 功能清单

### PM 的优先级指导
> 「我的想法是我们优先从项目管理、领域模型管理、业务流程管理这 3 个模块开始做」

### 开发顺序原则（PM 纠正）
PM 强调正确的思考顺序应该是：
1. 先确定 **MVP 要做什么**（概念层面：功能清单）
2. 再确定 **优先级**（哪些先做）
3. 最后才是 **如何做**（技术实现：技术栈、数据库 Schema 等）

### MVP 功能清单（31 项，按 5 大模块组织）

**模块一：项目管理（7 项）**
- 项目 CRUD、项目列表/搜索/筛选、项目详情查看、项目删除（软删除）、项目状态管理、项目成员角色管理、项目基本信息编辑

**模块二：领域模型管理（8 项）**
- 实体 CRUD、实体列表/搜索、字段 CRUD、字段类型约束（26 种）、实体间关系定义、关系可视化（ER 图）、领域模型导入/导出、数据流向自动推导（Phase 3 前置）

**模块三：业务流程管理（8 项）**
- 流程 CRUD、全局节点池管理（CRUD）、边管理（CRUD）、流程-节点关联管理、流程图渲染（前端）、节点类型校验、循环检测与警告、子流程嵌套支持

**模块四：应用与页面管理（5 项）**
- 应用 CRUD、页面 CRUD、页面布局区域定义、页面导航配置、页面与流程关联

**模块五：系统基础（3 项）**
- 用户认证与授权、操作审计日志、系统配置管理

## 第五部分：数据库 Schema 设计

### 设计规范（PM 确认）
- `created_at` / `updated_at` 作为统一标准字段，所有数据库表都必须包含
- `entity_relations.type` 简化为 2 个值：`has` / `belongsTo`（数量关系由独立 cardinality 字段表达）

### 核心表（12+ 张）

**项目管理（1 张）**
- `projects` — 项目主表（id, name, display_name, description, status, version, config JSONB, created_at, updated_at）

**领域模型（4 张）**
- `domain_entities` — 实体表
- `entity_fields` — 字段表（26 种字段类型）
- `entity_relations` — 实体关系表（type: has/belongsTo, cardinality, source_config/target_config JSONB）
- `data_flow_metadata` — 数据流向元数据表（自动推导结果存储）

**业务流程（5 张）**
- `business_processes` — 流程定义表
- `process_nodes` — 全局原子节点池（Action/Decision/Start/End/Parallel/Fork/Join/Merge）
- `process_edges` — 全局边池
- `process_node_map` — 流程-节点关联映射表（含 sort_order=0 入口节点语义）
- 注：不需要 process_edge_map，边的归属可通过两端节点是否在同一流程的节点集中推导

**应用与页面（3 张）**
- `applications` — 应用定义表
- `pages` — 页面表
- `page_layout_regions` — 页面布局区域表

### 样例数据
以「换电站管理系统」为例，设计了完整的样例数据用于开发和测试。

## 第六部分：RESTful API 设计

### API 总览（40+ 端点）

| 模块 | 端点数 | 示例 |
|------|--------|------|
| 项目管理 | 7 | GET/POST /api/projects, GET/PUT/DELETE /api/projects/:id |
| 领域模型·实体 | 7 | GET/POST /api/projects/:id/domain/entities, ... |
| 领域模型·字段 | 6 | GET/POST /api/projects/:id/domain/entities/:entityId/fields, ... |
| 领域模型·关系 | 5 | GET/POST /api/projects/:id/domain/relations, ... |
| 业务流程·流程 | 7 | GET/POST /api/projects/:id/processes, ... |
| 业务流程·节点 | 6 | GET/POST /api/projects/:id/process-nodes, ... |
| 业务流程·边 | 5 | GET/POST /api/projects/:id/process-edges, ... |
| 流程-节点关联 | 4 | GET/PUT/DELETE /api/projects/:id/processes/:pid/nodes, ... |
| 应用 | 5 | GET/POST /api/projects/:id/applications, ... |
| 页面 | 6 | GET/POST /api/projects/:id/applications/:appId/pages, ... |

### 关键设计决策
- 统一前缀 `/api/projects/:projectId/...`（资源嵌套于项目下）
- 软删除（status 字段标记，不物理删除）
- 分页、排序、筛选标准化
- 响应格式统一 `{ data, meta: { total, page, pageSize } }`

## 第七部分：校验机制技术方案（Task 1.5）

### 产出文档
`docs/04-tech-design/validation-design.md`（~370 行，v1.0）

### 核心结论

| 决策编号 | 决策 | 理由 |
|----------|------|------|
| VAL-1 | TypeBox + Ajv | 一套定义三处复用：TS 类型 + 运行校验 + JSON Schema 输出 |
| VAL-2 | 四层校验模型 | L1/L2/L3 Phase 1 实现，L4 Phase 2 实现 |
| VAL-3 | 动态 Schema 分发 | 按 component.type 从注册表查找对应 PropsSchema |
| VAL-4 | Ajv allErrors 模式 | 一次返回全部错误，减少反复修改次数 |
| VAL-5 | Fastify preValidation 集成 | 路由层统一拦截，业务代码无需关心校验 |
| VAL-6 | JSON Schema 原生输出 | TypeBox.Sprint() 零成本输出，供 Phase 4 MCP 使用 |

### 四层校验模型

| 层级 | 名称 | 范围 | Phase |
|------|------|------|-------|
| L1 | 结构校验 | 必填字段、类型匹配、枚举值合法 | Phase 1 |
| L2 | 类型约束校验 | Props 符合组件类型的 PropsSchema | Phase 1 |
| L3 | 引用完整性校验 | Hook 事件存在性、navigate 目标存在、binding 引用有效 | Phase 1 |
| L4 | 跨对象一致性校验 | 域模型字段引用、流程图一致性、角色权限引用 | Phase 2 |

│   │   ├── src/

│   │   │   └── utils/          # 共享工具函数

│       ├── src/
│       └── package.json
├── workspace/
│   └── dev/                    # 开发环境配置（Docker Compose 等）

- PostgreSQL 通过 Docker Compose 在本地运行
