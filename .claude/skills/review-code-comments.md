# review-code-comments — 注释质量审查

> **触发时机**：commit 前 / code review 时 / 用户显式调用
> **目的**：审查代码注释的完整性、准确性、质量，输出结构化审查报告

---

## 审查维度

### D1：文件头注释完整性

| 检查项 | 标准 |
|--------|------|
| 每个 `.ts` / `.tsx` 文件是否有 `@module` + `@description`？ | 必须有 |
| 复杂模块是否引用了 `@related` 设计文档？ | 建议有 |

### D2：函数/类注释覆盖率

| 检查项 | 标准 |
|--------|------|
| 所有 `export` 的函数是否有 docstring？ | 必须 100% 覆盖 |
| 类是否有 class-level 注释说明职责？ | 必须 |
| docstring 是否包含参数含义和返回值说明？ | 复杂函数必须 |

### D3：分支注释覆盖率

| 检查项 | 标准 |
|--------|------|
| 所有 `if` / `else if` / `else` 是否有分支注释？ | 必须，除非分支体 ≤ 1 行且显而易见 |
| 所有 `switch` 的 `case` 是否有 case 注释？ | 必须 |
| 三元表达式嵌套或含业务逻辑时是否有注释？ | 必须 |

### D4：长代码块检查

| 检查项 | 标准 |
|--------|------|
| 有无超过 10 行连续代码无段落注释的块？ | 不允许 |
| 循环体（for/while）是否有循环目的注释？ | 建议 3 行以上必须有 |

### D5：注释准确性

| 检查项 | 标准 |
|--------|------|
| 注释描述的行为是否与代码实际行为一致？ | 必须一致 |
| 有无过时/错误/误导性注释？（如「TODO: fix later」无编号） | 不允许 |
| 魔法数字/正则是否有解释「为什么」的注释？ | 必须有 |

---

## 输出格式

审查完成后输出以下格式报告：

```markdown
## 注释审查报告

**审查范围**：[涉及的文件列表] 或 [commit hash]
**审查人**：Claude Code (auto)

### ✅ 通过项
- `src/app.ts` — 文件头 + 函数注释完整，分支覆盖 100%
- `src/routes/projects.ts` — 分支注释完整

### ❌ 问题项

| 文件:行号 | 规则 | 问题 | 建议修复 |
|----------|------|------|------|---------|
| `src/services/project.service.ts:45-62` | R4 | 18 行查询逻辑无段落注释 | 添加 `// 查询项目列表：先查总数再查分页` 段落注释 |
| `src/services/project.service.ts:78` | R3 | else 分支缺少注释 | status === 'archived' 归档项目的处理逻辑未说明 |
| `src/models/schema.ts:12` | R5 | `$defaultFn` 替代 defaultRandom 无 why 注释 | 补充「Drizzle 0.38.x 不支持 defaultRandom()」原因 |

### 📊 统计
- 文件数：X
- 通过率：Y/Z (XX%)
- 主要问题类型：[R3 分支缺失 / R4 长块遗漏 / R5 缺 why]
```

---

## 执行流程

1. 扫描目标文件（变更文件 / 全量文件 / 指定路径）
2. 按 D1-D5 五个维度逐项检查
3. 记录每个问题：文件路径 + 行号范围 + 违反的规则 + 具体问题描述
4. 输出结构化报告（通过项 + 问题项 + 统计）
5. 如果问题数 > 0，建议用户修复后再 commit
