# review-code-comments — 注释质量审查

> **触发时机**：commit 前 / code review 时 / 用户显式调用
> **目的**：审查代码注释的完整性、准确性、质量，输出结构化审查报告

---

## 审查维度

### D1：文件头注释完整性

| 检查项 | 标准 |
|--------|------|
| 每个 `.ts` / `.tsx` 文件是否有 `@module` + `@description`？ | 必须有 |
| 复杂模块是否引用了 `@related` 设计文档？ | 建议有 |

**严重级别**：❌ 缺失 = 阻断级（必须修复才能提交）

### D2：函数/类注释覆盖率

| 检查项 | 标准 |
|--------|------|
| 所有 `export` 的函数是否有 docstring？ | 必须 100% 覆盖，无例外 |
| 类是否有 class-level 注释说明职责？ | 必须 |
| docstring 是否包含参数含义和返回值说明？ | 函数体 > 3 行或有分支/I/O 时必须 |

> **「复杂函数」的判定标准**（满足任一即算复杂）：
> - 函数体超过 3 行
> - 包含 if/switch/try 等分支或异常处理
> - 执行数据库/网络 I/O
> - 返回值类型不是简单字面量
>
> **不满足以上所有条件的极简函数**（如 `return a + b;`）可只写一行说明。

**严重级别**：❌ 缺失 = 阻断级

### D3：分支注释覆盖率

| 检查项 | 标准 |
|--------|------|
| 所有 `if` / `else if` / `else` 是否有分支注释？ | 必须，除非分支体 ≤ 1 行且显而易见（如 `if (!row) throw ...`） |
| 所有 `switch` 的 `case` 是否有 case 注释？ | 必须 |
| 三元表达式嵌套或含业务逻辑时是否有注释？ | 必须 |

**严重级别**：⚠️ 缺失 = 建议修复（影响可读性但不阻断）

### D4：长代码块检查

| 检查项 | 标准 |
|--------|------|
| 有无超过 10 行连续代码无段落注释的块？ | 不允许 |
| 循环体（for/while）是否有循环目的注释？ | 建议 3 行以上必须有 |

**严重级别**：⚠️ 缺失 = 建议修复

### D5：注释准确性

| 检查项 | 标准 |
|--------|------|
| 注释描述的行为是否与代码实际行为一致？ | 必须一致 |
| 有无过时/错误/误导性注释？（如「TODO: fix later」无编号） | 不允许 |
| 魔法数字/正则/业务规则是否有解释「为什么」的注释？ | 必须有 |

**严重级别**：
- ❌ 注释与代码矛盾 = 阻断级
- ⚠️ 缺少 why 型注释 = 建议修复

## 输出格式

审查完成后输出以下格式报告：

```markdown
## 注释审查报告

**审查范围**：[涉及的文件列表] 或 [commit hash]
**审查人**：Claude Code (auto)

### ✅ 通过项
- `src/app.ts` — 文件头 + 函数注释完整，分支覆盖 100%

### ❌ 问题项

| 文件:行号 | 维度 | 严重度 | 问题 | 建议修复 |
|----------|------|--------|------|---------|
| `src/services/project.service.ts:45-62` | D4 | ⚠️ | 18 行查询逻辑无段落注释 | 添加 `// 查询项目列表：先查总数再查分页` 段落注释 |
| `src/services/project.service.ts:78` | D3 | ⚠️ | else 分支缺少注释 | status === 'archived' 归档项目的处理逻辑未说明 |
| `src/models/schema.ts:12` | D5 | ⚠️ | `$defaultFn` 替代 defaultRandom 无 why 注释 | 补充「Drizzle 0.38.x 不支持 defaultRandom()」原因 |
| `src/routes/projects.ts:1` | D1 | ❌ | 缺少文件头 @module + @description | 添加文件头注释说明路由前缀和端点列表 |

### 📊 统计
- 审查文件数：X
- 阻断级问题：N 个（必须修复）
- 建议修复问题：M 个
- 通过率：Y/Z 规则项 (XX%)
- 主要问题类型：[D2 函数缺失 / D3 分支缺失 / D4 长块遗漏 / D5 缺 why]

### ✅ 结论
- [ ] 通过 — 可以提交
- [ ] 不通过 — 请先修复阻断级问题后再提交
```

---

## 执行流程

1. 扫描目标文件（变更文件 / 全量文件 / 指定路径）
2. 按 D1-D5 五个维度逐项检查
3. 记录每个问题：文件路径 + 行号范围 + 违反的维度 + 严重度 + 具体问题描述
4. 输出结构化报告（通过项 + 问题项 + 统计 + 结论）
5. 如果存在阻断级（❌）问题，明确告知用户「不通过，请先修复」
6. 如果仅有建议修复（⚠️）问题，告知用户「通过但建议优化」
